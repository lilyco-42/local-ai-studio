# i18n：两条轴，别混成一件事

日期 2026-10-19 · 权重与字典的大小来自 `oar-ocr` 的 `docs/models.md` 表格与 release 产物 API 实测；
`digest` 字段同样逐条存在（见 ADR-0001 的更正），所以这些语言包可以按 sha256 钉。
—— 2026-10-20 补：这句概括是对的，但它没说出真正难的地方。下面《A 轴的 pin 到底能钉到哪一级》
量了四件事：产物只在四个老 release 里、**同一文件名在两个 tag 下是两个不同文件**、
上游另有一个 ModelScope 镜像（两家哈希一致，因此能到 4.5 级）、
以及繁中/日/格鲁吉亚的字典**两家都没有**，只能按 commit 自算。

这个产品里"i18n"其实是两件独立的事，成本和做法完全不同：

| 轴 | 内容 | 加一种语言要什么 | 体量 |
|---|---|---|---|
| **A. 识别能力** | OCR 能不能认出这种文字 | 换一个 `*_rec.onnx` + 配套 `*_dict.txt`，**不改代码** | rec 7.4–12.8 MiB，dict 1.9–75 KB |
| **B. 界面语言** | 菜单/提示/错误文案 | 翻译资源 + 复数/语序规则 | 与模型无关，纯前端 |

把两件事写进同一个开关是这类产品最常见的坑：用户以为"我选了泰语界面就能读泰语图片"，
实际上前者是文案、后者是换权重。

## A 轴实测：上游到底给了哪些语言

`docs/models.md` 把识别权重分成两张表：**Chinese/General Models** 与 **Language-Specific Models**。

- **简体中文不是"语言包"，它是通用模型的本职**：`### Chinese/General Models` 下是
  `ch_svtrv2_rec.onnx`(80.3 MiB)、`ch_repsvtr_rec.onnx`(24.2 MiB) 与 PP-OCRv3/v4/v5 的 ch 系列；
  最新的 PP-OCRv6 走的是不带语言前缀的
  `pp-ocrv6_tiny/small/medium_rec.onnx`（**4.3 / 20.2 / 73.0 MiB**），
  配 `ppocrv6_tiny_dict.txt`(6,904 字 / 27,156 B) 与 `ppocrv6_dict.txt`(18,708 字 / 74,947 B)。
  字典里 18,708 个字符这个事实就是"通用包覆盖中日韩"的直接证据，不用猜。
- **Language-Specific 一共 14 种、23 个权重**（表里 23 行是"各代全都要"的数；每种只取最新版是 14 行。
  2026-10-20 现算：**14 行 rec + 配套字典 = 117.6 MiB**，再加共享的
  `pp-ocrv5_mobile_det.onnx` 4,826,518 B = **122.2 MiB**。数字由 `tools/ocr_language_pins.py`
  从四张真表逐条相加，不是抄本文早先那两个数；早先写的 117.5 / 122.1 少了三个外部字典的 51,227 B）：

### 三个必须写进产品的事实

1. **多语言 OCR 便宜到可以不设限**：14 种语言最新版（含各自字典与共享 det）合计 **122.2 MiB**。
   按实测国内 R2 的 0.82–1.01 MiB/s 约 **2–3 分钟**就能全部下齐。
   这和对话(395.9 MiB 起)、生图(1,494.2 MiB 起)完全不是一个量级，
   所以 OCR 的语言**不该做成"高级功能"**，做成一次可选的多语言包更符合"普通人电脑"这个目标。
2. **繁中、格鲁吉亚语只有 PP-OCRv3 的语言包**，日文也只有 v3 专属包。
   这不是"没支持"，而是**质量上限停在一代之前**：给这些 locale 的承诺不能写成与中英同级，
   要在 UI 里如实标"该语言的专用识别模型较旧"，并允许回落到通用 v6（通用字典 18,708 字符含 CJK）。
3. **权重与字典必须成对下载**：每种语言的 `*_dict.txt` 是独立文件（1.9–75 KB）。
   只下 rec 不下 dict 会静默出乱码，所以目录里每条语言项要同时记两个 sha256，
   下载与校验也按这一对做原子处理。
   —— 2026-10-20 这条已经落成数据：`pins/ocr-languages.json` 每语言一条，rec 与 dict 各带
   `sha256 / size / sources / level`，由 `tools/ocr_language_pins.py` 现算现钉，不是手抄。

## A 轴的 pin 到底能钉到哪一级（2026-10-20 按四张真表逐条量）

这一节推翻本文早先那句"digest 字段同样逐条存在，所以可以按 sha256 钉"的**概括**——
结论没错，但过程里有四个坑，每一个都能让"按名字找产物"的朴素实现钉错文件：

| 事实 | 实测数字 | 对产品的影响 |
|---|---|---|
| 语言权重不在最新 release 里 | 产物只存在于 **v0.1.0 / v0.3.0 / v0.6.0 / v0.7.0** 四个 release；v0.4.0 一直到 v0.9.2 的**产物数是 0** | "取最新 release 的资产"这种写法直接落空，必须按 models.md 每条链接里的 tag 定位 |
| **同名不同物**：一个文件名在两个 tag 里是两个不同文件 | 112 个产物名里 7 个跨 tag 重名，其中 **2 个内容不同**：`ppocrv5_latin_dict.txt` 在 v0.1.0 是 1,634 B / `3c0a8a79…`，在 v0.3.0 是 2,616 B / `ccbcc457…`（另一个是 `uvdoc.onnx`） | 按名字找"第一个命中"会把拉丁语字典钉成另一份文件。第一版就是这么写的，`--live` 报"来源哈希不一致"才逼出来 |
| 上游自己有**第二个分发方** | `oar-ocr-core/src/core/download/registry.rs` 是 name → sha256+size 的登记表，文件头写明对象镜像在 **ModelScope `greatv/oar-ocr`**；实测 ModelScope 101 个文件，GitHub 的 112 个产物里 **94 个两边都在**，且两家哈希逐字符相等 | 语言包不是"只有一家给哈希"的 3 级，而是**两家分发方元数据一致**的 **4.5 级**（仍是同一作者，够不到第 6 级） |
| 三个 v3 语言的字典**两家都没有** | `chinese_cht_dict.txt` / `japan_dict.txt` / `ka_dict.txt` 不在 GitHub 产物也不在 ModelScope；models.md 明写"不在 auto-download 注册表内，从 PaddleOCR 取再把本地路径传给 rec builder"，链接指着 `blob/main/…`（可变分支） | 只能"解析成一个 commit + 取 raw 整文件自算 sha256"。这正对应上面那条 ⚠：**繁中/日/格鲁吉亚的语言轴是打折的** |

量出来的合计（`pins/ocr-languages.json`，与 `tools/ocr_language_pins.py --live` 可重跑）：

- 14 种语言 × (rec + dict) = **117.6 MiB**，再加共享 `pp-ocrv5_mobile_det.onnx`（4,826,518 B，4.5 级）
  = **122.2 MiB**。本文早先写的 117.5 / 122.1 是**只算 release 内文件**的结果 ——
  三个外部字典合计 51,227 B，四舍五入正好吃掉 0.1 MiB。
- 层级分布：**4.5 级 25 条**、**自算 + 钉 commit 3 条**（就是上面那三个字典）。
- 聚合值不是手抄的：`rec_dict_bytes` 由逐条相加得出，车道 `ocr-languages` 每次重算一遍并对不上就红。

守门的车道是 `ocr-languages`（三步各查一件事，缺一不可）：① 已提交 pin 对照仓库快照；
② 对照上游四张表现状；③ 现场重立一张，逐字段与提交的那张比。
第③步**有意忽略 `pinned_commit` / `resolved_url`** —— PaddleOCR 的 `main` 一直在动，
那两条每天都不同，参与比对会让车道天天红，最后被当成噪声，等于没有守门人。
字典内容本身（`sha256`）照样要相等。


## 默认集建议（等你拍板）

上游的 det 也是分代的（实测 release 产物）：`pp-ocrv6_tiny_det`(1.69) /
`pp-ocrv6_small_det`(9.42) / `pp-ocrv6_medium_det`(59.15) MiB，另有跨代通用的
`pp-ocrv5_mobile_det`(4.6) 与 v4 系列。所以按"同代成对"给三个候选：

- **极低配（≈6.0 MiB）**：`pp-ocrv6_tiny_det.onnx` 1.69 + `pp-ocrv6_tiny_rec.onnx` 4.3
  + `ppocrv6_tiny_dict.txt` 27,156 B；
- **默认（≈29.7 MiB）**：`pp-ocrv6_small_det.onnx` 9.42 + `pp-ocrv6_small_rec.onnx` 20.2
  + `ppocrv6_dict.txt` 74,947 B（18,708 字符，覆盖简中 + 英 + 常用 CJK）；
- **可省一代体积的混搭（≈24.9 MiB）**：通用 `pp-ocrv5_mobile_det.onnx` 4.6 + v6 small rec 20.2
  + 字典 —— 混代能用（det 与 rec 是独立网络），但要作为**显式选择**记进目录，
  不能默认混用，否则同一份"默认包"在不同版本间漂移时说不清到底装了哪一代。

- **可选包**：其余 13 种语言按需，单个 7.5–12.8 MiB；一键"全部多语言"≈ 122 MiB。
- **界面语言（B 轴）**：建议先 zh-CN / en 双语进 MVP，再按你实际用户补；
  这一轴与 A 轴解耦，加一种界面语言不动任何权重。

### 一个必须写进目录设计的实测陷阱

上游有两个名字只差一个连字符的 det：`pp-ocrv4_mobile_det.onnx`(v0.3.0, 4,826,518 B,
`sha256:ab2a50dc…`) 与 `ppocrv4_mobile_det.onnx`(v0.1.0, 4,782,456 B, `sha256:fd9d4f9b…`)。
**大小与哈希都不同，是两个不同产物。** 所以目录的键必须是 `<版本>/<文件名>` + sha256 三者一起，
只按文件名索引会在老标签里取到另一份权重，而且不会报错——只会识别质量莫名其妙地变差。

## 字幕的语言轴（whisper，实测 100 种）

A 轴讲的是 OCR 认哪些字；字幕是另一条轴，来源也不同 —— 引擎自己的语言表。
`tools/recommend_subtitle.py` 在钉住的 `whisper.cpp b5454` 上量到（读 `src/whisper.cpp:286` 的
`g_lang`，`zh` 那一行在 `:288`，已进 `pins/citations.json`）：

- **100 种语言，id 从 0 连续到 99**：`en`=0、`zh`=1、`ko`=5、`fr`=6、`ja`=7 …… `yue`=99（粤语单列）。
  id 连续不是巧合，是 `whisper.h` 里那句"`lang_probs` 数组必须开 `whisper_lang_max_id() + 1` 大小"
  的前提，所以工具把连续性当判据 —— 上游插一个不连续的 id，这里就该红。
- **`.en` 模型只有英文**：上游在 `models/README.md:63` 明写
  "Models are multilingual unless the model name includes `.en`"。这条直接决定 UI 行为：
  用户选了 `tiny.en` / `medium.en` 这类档，语言下拉就**只能剩英文**，
  而不是留着 100 项让他选了中文然后出一堆英文垃圾。
- **语言下拉不该由我们抄表**：100 个名字抄进 JSON 就等于给自己造了一个会过期的副本。
  外壳应该运行时问引擎（`whisper_lang_str` / `whisper_lang_id`，`include/whisper.h:358-369`），
  我们这张表只用来**量宽度、盯漂移**，并给"中文视频默认选哪颗模型"这条推荐提供依据。

与 A 轴的差别要写清楚，别混成一个数字：OCR 那一侧是 **14 种语言 / 23 个 rec 权重**
（受上游语言包供应限制），字幕这一侧是 **100 种**（引擎内建，不需要额外下载语言包，
只有模型文件本身要下）。所以"这个版本支持多少种语言"这种话必须带轴名，不然就是虚标。

## 与"模型自选"的边界

按你定的口径，"无审查"是本地自选模型，不做产品卖点也不做策展清单；
本文件只谈 OCR/界面语言，不涉及模型内容的道德分级。
